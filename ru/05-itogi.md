# Итоги

Мы прошли путь от «LLM не знает о выходе новой версии Spring» до архитектуры, в которой LLM сама расследует алёрты и выдаёт конкретный action plan. Давайте зафиксируем главное.

## Что мы построили

```          ┌──────────────────┐
           │   Claude Desktop │
           │   VS Code Copilot│
           │   Ваш чат        │
           └────────┬─────────┘
                    │
           ┌────────┴─────────┐
           │   MCP Client     │  ← ChatClient + автоподключение tools
           │   (Spring Boot)  │
           └────────┬─────────┘
                    │ JSON-RPC (Streamable HTTP)
           ┌────────┴─────────┐
           │   MCP Server     │  ← @McpTool, Resources, Prompts
           │   (Spring Boot)  │
           └────────┬─────────┘
                    │ mcp_readonly (только SELECT на VIEW)
           ┌────────┴─────────┐
           │   PostgreSQL     │
           │   Prometheus     │
           │   Kubernetes     │
           │   OpenSearch     │
           │   Jenkins        │
           │   Jira           │
           └──────────────────┘
```

Один MCP-сервер обслуживает и саппорта (сценарий 1), и автоматику (сценарий 2). Ни строчки кода не дублируется между потребителями.

## Ключевые выводы

**MCP убивает vendor-lock на уровне инструментов.** Написали `getBlockingSessions()` один раз — он работает и в вашем чате для саппорта, и в Claude Desktop, и в авто-расследовании. Переписывать под каждого клиента не нужно.

**Spring AI 2.0 сводит интеграцию к аннотациям.** `@McpTool` на методе — и он уже доступен LLM. `@Bean` с ресурсами и промптами — и у хоста есть контекст и сценарии. MCP-клиент подключается одной строкой: `.defaultTools(connectionManager.getToolCallbacks())`. Транспортный слой скрыт автоконфигурацией.

**Безопасность — не опция, а архитектура.** MCP-сервер подключается к БД под ролью `mcp_readonly`, которая имеет SELECT только на VIEW в схеме `mcp_api`. LLM физически не может прочитать PII и тем более изменить данные. Что бы модель ни «придумала» — у неё нет прав на DELETE, UPDATE или TRUNCATE. Для продакшена этот уровень защиты не «best practice», а необходимость.

**Три примитива — три источника инициативы.** Tool вызывается LLM, Resource загружается хостом, Prompt выбирается пользователем. Это разделение принципиально: оно разграничивает зоны ответственности между моделью, приложением и человеком.

**Главная победа — не в коде, а в том, как меняется работа.** Саппорт расследует проблему за минуту вместо часа. Ночные алёрты разбираются автоматически, без вызова дежурного. Разработчик не пишет интеграции под каждый новый клиент — он один раз описывает инструменты, и они доступны везде.

## Что дальше

MCP быстро развивается. Вот что стоит держать в фокусе:

- **MCP Hub** — каталог готовых MCP-серверов для популярных систем (PostgreSQL, Prometheus, Jira, Slack). Возможно, ваш следующий MCP-сервер уже написан и ждёт вас в каталоге.
- **OAuth 2.1 в MCP** — спецификация уже поддерживает авторизацию для удалённых подключений. Если ваш MCP-сервер открыт наружу, OAuth становится обязательным.
- **Мониторинг самого MCP** — rate limiting, аудит вызовов tools, алёртинг на аномальную активность LLM. MCP-сервер — такое же production-приложение, как и все остальные.
- **Стриминг ответов** — в спецификации 2025 появился Streamable HTTP, который позволяет передавать частичные результаты tool-вызовов. Длинные расследования можно показывать пользователю по мере выполнения, а не ждать финала.
